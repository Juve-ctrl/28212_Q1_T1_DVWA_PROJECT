Assessment category: API Security

1. REMEDIATION SUMMARY

The API Security category was addressed in the separate hardened DVWA environment. The changes focused on protecting user data, restricting user updates, preventing command injection, protecting token-signing secrets, externalising OAuth client credentials, and enforcing Bearer-token authentication for order requests.

2. IMPLEMENTED PROTECTIONS

A. User data exposure

The user API serialization was modified to return only the permitted user fields: id, name, and level. Password hashes are excluded from API responses.

B. Mass assignment

User creation and update input validation was restricted. User updates accept the name field only, with validation for its type, non-empty value, and maximum length. Attempts to submit an unauthorized level change are rejected.

C. Command injection

The health connectivity endpoint validates its target before executing a ping operation. The ping process is invoked using an argument array with shell bypass rather than interpolating user input into a shell command.

D. Token-signing secrets

Hardcoded token-signing secret constants in Login.php were replaced with environment-based secret retrieval. The application validates that the configured secrets are 64 hexadecimal characters. The hardened environment file is permission-restricted.

E. Bearer-token authentication

The order API checks the access token supplied in the HTTP Authorization Bearer header before processing the protected order request.

F. OAuth client credentials

The demonstration client ID and client secret were removed from the login controller's hardcoded authentication comparison. The controller now reads the expected credentials from DVWA_API_CLIENT_ID and DVWA_API_CLIENT_SECRET environment variables. The hardened Compose configuration requires both variables, and the credentials are stored in the permission-restricted hardened environment file. The comparison uses hash_equals.

4. SECURITY CONFIGURATION NOTES

The OAuth client ID, OAuth client secret, access-token signing secret, and refresh-token signing secret are supplied through the hardened environment configuration rather than hardcoded authentication comparisons or token-signing constants. The environment file is permission-restricted. Secrets must remain confidential and should be rotated according to an appropriate operational policy.

5. CONCLUSION

The documented API protections have been implemented. The OAuth login and protected order endpoint were successfully verified using the new environment-based client credentials. The recorded negative tests rejected the mass-assignment and command-injection attempts.

This report records the implemented changes and observed tests. It does not, by itself, establish that every API route or the entire application is production-ready. Final submission evidence review and any remaining required checks must still be completed.
